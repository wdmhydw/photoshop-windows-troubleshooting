# Photoshop 放着不用就退出：一次网络变化触发崩溃的定位与兼容试验

记录日期：2026-11-02
验证环境：Windows 26H2（构建 26340.9843），Photoshop 2026 27.8.0.13，ASIX USB 有线网卡。

我的现象是：PS 一直用着通常比较稳定，整台电脑放着不动，回来时 PS 却自己退出了。后来确认，网络连接状态变化可以触发其中一类退出。排查定位到了网络检测中的同线程锁重入路径；对本机确切程序做局部兼容修改后，六轮网络重连均通过，其中一轮在重启 PS 后完成。

这个结果覆盖本机已复现的网络触发场景。长时间待机、整机睡眠唤醒，以及文字编辑卡死尚未完成同样的验证。

## “网络变化”这条线索来自哪里

本机多个崩溃时间紧跟网络状态变化。异常代码为 0xe06d7363，Windows 事件显示故障模块 KERNELBASE.dll。

仅凭这个异常代码还不足以判断根因。进一步看转储，发现 Windows 网络列表管理器 netprofm、COM/RPC 回调以及 PS 网络检测函数出现在同一条异常路径中。

Adobe 社区已有一篇相似的睡眠唤醒崩溃报告，也包含网络状态通知和 COM/RPC 路径。该报告帮助明确了值得调查的方向；下面的参数、锁类型和试验结果来自本机，需要分别核对。[1]

## 崩溃发生在什么地方

本机转储与静态检查支持以下过程：

    PS 网络检测取得互斥锁
        ↓
    调用 Windows Network List Manager 的 GetConnectivity
        ↓
    COM STA 等待过程中处理回调，再次进入 PS 网络检测
        ↓
    同一线程再次锁定原来的非递归锁
        ↓
    抛出 std::system_error，PS 退出

本机 _Throw_Cpp_error 的实参是 5，对应 RESOURCE_DEADLOCK_WOULD_OCCUR。类型信息确认相关对象属于 uxtech::network::ReachabilityImpl。Microsoft STL 实现也提供了核对锁行为与标志值的依据。[2][3]

这里应以实际调用位置、导入函数及类型信息为准。缺少完整私有符号时，调试器显示的附近导出符号名，容易让人误以为异常属于其他模块。

## 哪些调整只起到缓解作用

关闭启动首页，以及关闭 USB 网卡的若干节能选项后，一次重连通过了。但 17:06 的后续重连仍触发相同崩溃。

这个反例很重要：减少触发频率和修正程序内部的异常路径，验证标准不同。一次通过还不足以证明间歇性崩溃已经消失。

## 本机做了什么兼容试验

完整备份程序并核对文件哈希、类型信息和构造代码后，只调整了网络状态对象的一处锁初始化属性：从非递归锁标志 0x2 调整为允许同线程重入的 0x102。正常加锁、解锁和网络查询仍然执行。

这是为本机二进制制作的局部兼容试验，涉及主程序一个字节。版本号相同的其他文件也可能有不同布局，其他互斥锁更可能有不同的状态约束。公众复现应优先验证异常路径；具体二进制修改需要重新核对对象、指令和完整文件身份。

本机安装在本轮之前已经包含本地程序修改，网络试验也没有成为完整的干净安装对照。现有证据适合分享为问题定位和局部干预结果，官方修复仍有独立价值。

## 怎样验证结果

对照与修正后的结果如下：

    修正前：关闭首页、调整网卡节能后，17:06 仍复现崩溃。
    修正后：同一 PS 会话连续五轮断开重连，均恢复联网，PS 保持响应。
    重启后：再做一轮重连，也通过；本轮共六次成功。
    文档状态：测试文档及明确的未保存图层移动仍然保留。
    恢复功能：新恢复快照正常生成，异常退出后自动恢复，图层状态匹配。
    正常退出：测试文档关闭、PS 正常退出，再次启动均通过。

最终核对表明，原程序备份完整；把当前程序那个字节反向重建后，内容与备份逐字节一致。回滚准备与验证记录一起保留。

截至本文记录日，结论是“本机网络变化触发退出的局部修正通过六轮回归”，长期使用情况仍需后续记录。文字编辑卡死另行处理。

## 其他人排查时值得保留的信息

建议记录具体 PS 版本、Windows 版本、网络变化类型、崩溃事件时间和转储中的相关调用栈。若网络变化与崩溃紧邻，而且栈中出现 netprofm、GetConnectivity、COM/RPC 和 _Throw_Cpp_error，就有理由进一步检查网络状态回调。

本案最有用的方法是让事件时间、实际调用栈和修改后的复测相互验证。只凭“放着不用就退出”，很容易把所有问题都归到显卡、字体或内存上。
